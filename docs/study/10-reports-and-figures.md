# Module 10 — Reports, figures and cross-run comparison

**Files covered:** `src/model_training/reports/experiment_report.py`, `src/model_training/reports/model_card.py`, `src/model_training/reports/comparison.py`, `src/model_training/reports/figures.py`, `scripts/plot_results.py` (`reports/__init__.py` was covered in Module 1)

**Where we are:** Modules 3–9 wrote every artifact a run produces. This module turns them into what people read: an experiment report, a model card, per-run figures, a cross-run comparison table, and the README's results figure. If an earlier module is honest and this one misreports it, the honesty is lost at the last step. So this module checks presentation against source.

**The one-line thesis:** The report and model card follow a strong discipline: every section always renders, and anything missing says "not run" or "unavailable" instead of disappearing. But the report is built from in-memory state despite claiming otherwise, it drops a real number (this repo's git commit, SmolVLA's MAE), the comparison table has no seed aggregation despite the docs, and the README figure script hard-codes the very selection points it claims to read from disk.

---

## 10.1 Prerequisites — the absolute basics

- **Experiment report.** A human-readable record of one run: hypothesis, data, configuration, results, limitations, conclusion. Here it's `reports/experiment_report.md`.
- **Model card.** A short document attached to a trained model describing intended use, training data, evaluation results and limitations. The convention comes from Mitchell et al. (2019). Here it's `reports/model_card.md`.
- **"Absent vs not run".** In a report, an omitted section is ambiguous: was the thing not done, or did it fail silently? Always rendering the section, with an explicit "not run", removes that ambiguity. It's the reporting version of the project's "never fabricate" rule.
- **Matplotlib backend.** The rendering engine. `Agg` is a non-interactive raster backend that works without a display (servers, CI). `matplotlib.use("Agg")` sets it *process-wide*.
- **Figure lifecycle.** Each `plt.subplots()` allocates a figure that stays in memory until `plt.close(fig)`. Long loops that never close figures leak memory, and matplotlib warns after 20 open figures.
- **Reproducible figure.** A figure generated by a script from stored data, so it can be regenerated identically, as opposed to a hand-edited plot. The test is whether the script contains *any* hard-coded number that belongs to the data.
- **Seed aggregation.** Reporting mean ± standard deviation (or a confidence interval) over runs that differ only in random seed.

## 10.2 `render_experiment_report`

```python
def render_experiment_report(ctx: dict[str, Any]) -> str:
    """``ctx`` carries everything the report cites; see ExperimentRunner for exactly what it
    assembles. Fields that were not run/available render as stated text
    ("not run", "unavailable") rather than being omitted silently."""
```

**Decision: fixed sections, with explicit "not run" text.** Every section heading (Objective, Dataset, Model, Training configuration, Compute environment, Test metrics, Baselines, Stratified, Failure analysis, Rollout, Limitations, Conclusion, Data feedback recommendation) renders whether or not it has data. A baseline-only run still shows "Test metrics ... _not run_" and "Closed-loop / rollout evaluation: unavailable". The runner test asserts `"unavailable" in report_text` (rollout must be stated, not omitted). *Why:* a reader can tell "absent" from "failed". *Alternative:* a template engine (Jinja2) with conditionals that hide empty sections. *Cost of the choice:* a longer report with some empty sections, which is the right trade.

**Doc vs code: "assembled entirely from saved run artifacts".** The module docstring says the report is "assembled entirely from saved run artifacts, never from mutable live state, so re-running this function against a finished run's directory always reproduces the same report". In fact:
- the function takes a `ctx` **dict built in memory by the runner** from live objects (`intervention_result`, `training_outcome`, `test_overall`, `profile`, `feedback_artifact`, Module 11), not from files;
- **no function exists that rebuilds `ctx` from a run directory**, and no CLI command regenerates a report;
- `ctx["generated_at"]` is `now()`, so even an identical `ctx` produces a different report.

The *values* in `ctx` match what was written to disk, because they come from the same objects at the same moment. So the report is *consistent with* the artifacts, but it isn't *derived from* them. Say "built from the same in-memory results the artifacts were written from", and say that a regenerate-from-disk command is missing.

The runner always *sets* `selected_checkpoint` (to `None` for baseline-only runs), so `.get(..., 'n/a')` returns `None` and the report prints `` `None` `` instead of `n/a`. The default only applies to a missing key, not to a `None` value. It's the same pattern as `_fmt`'s own `None → "n/a"`, which isn't used here. Cosmetic, but it's the "absent vs not run" discipline slipping.

```python

    lines.append(f"| **{cfg['training']['model']} (this run)** | {_fmt(ctx['model_test_mse'])} | "
```

**SmolVLA's MAE is printed as `n/a` in the baseline table**, though `test_metrics["overall"]["mae"]` is right there in `ctx`. Each baseline row shows its MAE, and the model under test doesn't. That's a hard-coded `n/a` for a number that exists.

```python
def _fmt(v, digits=4):
    if v is None: return "n/a"
    if isinstance(v, float): return f"{v:.{digits}g}"
    return str(v)
```
- **4 significant figures** (`g` format), so 0.023942 becomes `0.02394` and 1.0e-4 becomes `0.0001`. That's sensible for MSEs that range over orders of magnitude.
- A **NumPy `float32`** isn't a Python `float`, so it falls through to `str(v)` with full repr. Module 3's `default=str` concern again: harmless here, inconsistent display.

```python
def _metrics_table(metrics):
    rows = [(k, v) for k, v in metrics.items() if not isinstance(v, (list, dict))]
```
**Per-dimension MAE is a list, so it's dropped from the report.** README Table 4 (per-joint MAE, "error grows from the base of the arm toward the end effector") is one of the project's most interpretable findings. It isn't in any generated report. It must have been read out of `test_overall.json` by hand. That's a reporting gap that hides a real result.

- **Limitations** come only from the runner's list (no GPU, no torch, non-SmolVLA model). **The rebalanced caveat `EXPERIMENTS.md` §4 promises is never added** (Module 4 gap 8), and neither is the silent `best → final` fallback (Module 6 gap 3).
- **Conclusion** is always `None` from the runner, so every report says "_not yet written -- fill in after reviewing the metrics above._". That's honest (the code doesn't pretend to conclude), but it means every report is a draft by construction.
- **"Data feedback recommendation"** repeats `recommended_next_action`, which was already printed under Failure analysis. It's a duplicated section, and Module 8 showed the text is the same template every run.
- **No escaping.** `hypothesis` and `objective` text go into Markdown raw. A `|` in a hypothesis would break the following table only if it were inside one, and they aren't. Harmless in practice.

## 10.4 `comparison.py`

```python
def load_run_summary(run_dir):
    run_dir = Path(run_dir)
    if not run_dir.exists():
        raise FileNotFoundError(f"no run directory at {run_dir}")
    summary = {"run_dir": str(run_dir)}
    for name in ("dataset.json", "model.json", "manifest.json", "summary.json"):
        p = run_dir / name
        if p.exists():
            summary[name[:-5]] = json.loads(p.read_text())
    ...  # test_overall.json, baselines.json, stratified.json likewise
```

- **This one genuinely *is* "reproducible from disk"**, as its docstring says. It reads only saved files. Good.
- **`manifest.json` is never written by anything** (Module 3, gap S12), so `summary["manifest"]` is always absent. It's dead code that implies a file exists.
- **Missing files are silently skipped**, so a crashed run (no `summary.json`, no `test_overall.json`) yields a row of `None`s with no indication of *why*. There's no `status` to read (Module 3 gap 10).
- **A partially written JSON file** (Module 3 gap 1) raises `JSONDecodeError` and aborts the whole comparison.

```python
def build_comparison_table(run_dirs, metric="mse"):
    for rd in run_dirs:
        s = load_run_summary(rd)
        ...
        row = {"run_dir": ..., "model": model.get("architecture"), "dataset_id": ...,
               "training_version": ..., "intervention": dataset.get("kind"),
               metric: overall.get(metric)}
        for name, m in (s.get("baselines") or {}).items():
            row[f"{name}_{metric}"] = m.get(metric)
        rows.append(row)
```

- **There's no aggregation across seeds.** `docs/EXPERIMENTS.md` §7: "`mtrain compare` can then report the mean and standard deviation across the resulting run directories." **No mean, standard deviation or grouping code exists** (I grepped for `std`, `mean(` and `stdev` in `reports/` and `experiments/` and found nothing). Each run is one row. That's a documented feature that isn't implemented (gap logged in Module 4).
- **There's no check that the runs share a test set.** Rows from `baseline_full` and `reduced_data` sit side by side as if comparable, while Module 4 showed they're scored on different test episodes. The table should at least show each run's test-episode IDs or a hash of them.
- **Baseline columns are added per row**, so runs with different baseline sets produce heterogeneous rows. `write_comparison_csv` handles that correctly (union of keys, in first-seen order, via `csv.DictWriter`). The terminal table in `cli.py` doesn't. It builds headers from `rows[0].keys()` and adds cells *by position*. Checking rich's source shows `Table.add_row` appends headerless extra columns instead of raising. **So with heterogeneous rows, values land under the wrong headers, silently.** That's a Module 12 issue, flagged here because it's this function's output shape that triggers it.
- **`metric` names a key in `test_overall.metrics`.** `--metric mse` gets the split-level MSE (correct). There's no confusion with the per-episode misnamed "mse" (Module 7), because that lives in a different structure.

```python
def build_model_dataset_matrix(rows, metric="mse"):
    """The model x dataset table: one row per (model, dataset/intervention) pair."""
    return [{"model": r.get("model"), "dataset": r.get("training_version"),
             "intervention": r.get("intervention"), metric: r.get(metric)} for r in rows]
```
- **It's not a matrix and it's not called.** It's a projection of rows, one per run, and nothing in `src/`, `scripts/` or `tests/` calls it. It also keys "dataset" on `training_version`, which is *unique per run* (Module 4: every run mints a new `training/vN`), so even a real pivot on it would never group two runs together. Pivoting on `dataset_id` plus `intervention` is what "model × dataset" means.

## 10.5 `figures.py`

```python
import matplotlib
matplotlib.use("Agg")
import matplotlib.pyplot as plt  # noqa: E402

def _save(fig, path):
    path.parent.mkdir(parents=True, exist_ok=True)
    fig.savefig(path, dpi=150, bbox_inches="tight")
    plt.close(fig)
    return path
```

- **`matplotlib.use("Agg")` at import time** makes figure rendering work headless, so training boxes and CI need no display. *Cost:* it's a **process-wide side effect of importing the package**. `reports/__init__.py` imports `figures`, and the runner imports `reports`, so importing `model_training.experiments` in a Jupyter notebook switches the notebook's backend to Agg. Inline plots then stop appearing until you reset it. The fix is to create figures with the object API (`matplotlib.figure.Figure()` plus `FigureCanvasAgg`), which needs no global backend.
- **`plt.close(fig)` in `_save`** prevents the figure leak. Without it, a sweep over many runs would accumulate open figures. It's the non-obvious line that matters.
- **`dpi=150, bbox_inches="tight"`** are sensible defaults for PNGs in Markdown.

**The "never a fabricated placeholder chart" contract** (module docstring) is kept. Every function returns `None` or `[]` when there's nothing to plot (no records, missing keys, fewer than 2 fraction points). That's consistent with Module 7's `{"status": "no outcomes"}` returns.

Per-function notes:
- `plot_training_curves`: loss always; LR and grad-norm only if present. **`r["loss"]` is a hard key access**, so an engine change to the record shape is a `KeyError` that aborts the *run* (the call isn't guarded in the runner). Plotting can crash the whole run after training succeeded.
- `plot_validation_curve`: filters rows that have the metric. That's robust.
- `plot_error_distribution`: **a bar chart of four quantiles** (median, p90, p95, p99). It shows four numbers as bars, which is a weak encoding. A histogram or empirical CDF of the per-frame errors (all available in `test_overall.outcomes`) would show the actual tail shape.
- `plot_episode_length_distribution`: expects the engine's histogram entries with `lo`, `hi` and `count` (another undocumented-shape coupling, as in Module 5). The x-label says duration in seconds.
- `plot_task_distribution`: for single-task SO-100, a one-bar chart in every run.
- **`plot_model_comparison` and `plot_data_fraction_curve` are never called** (grep finds only their definitions). The data-efficiency curve, the deliverable `run_data_fraction_sweep` exists to produce, has no caller and no CLI path.

- **It reads `r["mse"]` from validation rows**, so it's tied to MSE regardless of `selection_metric`.

Honest phrasing: "the figure is generated by a script from the runs' metric files; the selection markers and annotations are set by hand for these runs."

## 10.7 Honest gaps to own before an interviewer finds them

1. **The report's model_training git commit always prints `n/a`** (key mismatch). *Consequence:* every report hides this repo's provenance.
2. **The report claims to be "assembled entirely from saved run artifacts"**, but it's built from in-memory `ctx`, with no regenerate-from-disk path, and it's timestamped. *Consequence:* an overclaim, and reports can't be rebuilt after a template fix.

9. **`build_model_dataset_matrix`, `plot_model_comparison` and `plot_data_fraction_curve` are uncalled.** The "matrix" pivots on per-run-unique versions. *Consequence:* the data-efficiency curve has no path to exist.
10. **`matplotlib.use("Agg")` at import is a process-wide side effect.** *Consequence:* importing the runner breaks inline plotting in notebooks.
11. **The model card's "Known failure modes" is a templated sentence** (Module 8), and it names an unexecuted loader. *Consequence:* the card implies model-specific analysis it doesn't contain.
12. **The rebalanced and selection-fallback limitations are never added to reports.** *Consequence:* the two caveats that matter most are missing.
13. **A plot `KeyError` (`r["loss"]`) can abort a run after successful training.** *Consequence:* a presentation bug destroys an expensive result's completion (no `summary.json`).
14. **`manifest.json` is read but never written; missing files are silently skipped.** *Consequence:* dead code, and crashed runs appear as rows of `None`.
15. **No unit tests for any reports module** (the only coverage is the runner test's existence and substring checks). *Consequence:* every bug above shipped unnoticed.

# Appendix A — Model answers to the drill

**A1. Absent vs not run.**
"Every section of the report always renders. If something didn't happen (no GPU, no fine-tuning, no rollout), the section says 'not run' or 'unavailable' with a reason instead of disappearing. That matters because an omitted section is ambiguous: it could mean 'skipped on purpose' or 'crashed silently', and in a results document that ambiguity is where overclaiming hides. Rollout is the clearest case. Every report states there's no simulator or robot, and the runner test asserts the word 'unavailable' is in the report. I'll admit the discipline slips in a couple of places: a baseline-only run prints a literal `None` for the selected checkpoint, and SmolVLA's MAE is hard-coded to 'n/a' even though it exists."

*Why that answer lands:* it explains the principle in terms of what it prevents, gives the tested example, and volunteers where your own code doesn't live up to it.

**A2. Why not Jinja2 or W&B?**
"The report is linear and small, so f-strings in one function keep it readable and dependency-free. Jinja would mostly add conditionals I deliberately don't want, because sections never hide. W&B gives you a dashboard, not a durable document. The report is meant to sit in the run directory next to the artifacts it cites, readable in ten years without a service. The real weakness isn't the templating choice, though. It's that the report is rendered from in-memory state at the end of the run, and there's no command to rebuild it from a run directory. I'd fix that by writing a `ctx` builder that reads only the saved artifacts, which `compare` already does for its own table."

*Why that answer lands:* it justifies the choice from the document's purpose, then redirects to the actual architectural flaw, with a fix grounded in code that already exists.

**A3. Regenerating past reports.**
"You can't, with what exists. The report is built from a context dict the runner assembles in memory at the end of each run, and there's no function or CLI command that reconstructs that dict from a run directory. So a template fix only affects future runs. The artifacts needed are all on disk (resolved config, dataset, profile, training outcome, evaluation, feedback), so the fix is a `build_report_ctx(run_dir)` function and an `mtrain report --run` command, with a test that regenerating a fresh run's report reproduces it apart from the timestamp. That would also make the docstring's 'assembled from saved artifacts' claim true."

*Why that answer lands:* a precise "no", the reason, and a fix with its own acceptance test. It also turns a doc overclaim into a concrete deliverable.

**A4. Is the README figure reproducible?**
"Partly. The data in it is: the curves and bars are read from each run's validation log and test and baseline JSON, so regenerating from the same run directories redraws the same data. But the script hard-codes things that belong to the data: the selected-checkpoint markers at steps 1,800 and 800, the 1,000-step resume offset, the learning-rate annotation and the axis limits. For these runs, those values are correct (the validation minimum really was at 1,800), but point the script at different runs and it either crashes looking up step 1,800 or rings the wrong point as 'selected'. The fix is to read the selection from each run's model.json, the offset from the base run's steps completed, and the LRs from the resolved configs."

*Why that answer lands:* it separates data reproducibility from annotation reproducibility, confirms that the published figure is correct, and gives the exact source each hard-coded value should come from.

**A5. "How do you compare experiments, and how do you know a difference is real?"**
"Comparison reads only saved artifacts, so `mtrain compare` works on runs from any session and gives one row per run: model, dataset version, intervention, test MSE, and each baseline's MSE on the same split. Knowing a difference is real is where the project is weakest, and I'd say so. Each experiment is a single seed. The test split is five episodes. The policy is stochastic: re-scoring moves MSE by up to five percent. The docs say compare reports a mean and standard deviation over seeds, but that isn't implemented. And runs with different data interventions are scored on different test episodes. So the one difference I'd defend is the 18% improvement from continued training, which is on the identical test split and well outside the measured inference noise. For anything else, I'd want a paired comparison on a shared test set, a bootstrap over episodes and at least three seeds."

*Why that answer lands:* it describes the mechanism, then gives an honest, specific accounting of uncertainty, picks the one claim that survives and explains why, and names the minimum evidence needed for the rest.

# Module 10 Summary — the one page to revise

**What this module is.** A Markdown experiment report and model card rendered at the end of each run, per-run PNG figures, a disk-only cross-run comparison table, and a script for the README figure. The "never omit, say not run" discipline is good; several values are lost or mislabelled on the way to the page, and two documented capabilities (seed aggregation, rebuild from disk) don't exist.

**Five claims to make cold**
1. Every report section always renders, and missing work reads "not run" or "unavailable". Rollout is always stated as unavailable, and that's tested.
2. Comparison reads only saved artifacts, so it's reproducible across sessions, with one row per run.
3. The report is rendered from in-memory state. There's no regenerate-from-disk path, despite the docstring.
4. There's no seed aggregation and no shared-test-set check in `compare`. Only continued training (same test split, 18%, outside about 5% noise) is defensible.
5. The README figure's data comes from disk, but its selection markers (1,800 and 800) are hard-coded.

**Decisions**

| Chose | Over | Because | Cost |
|---|---|---|---|
| f-string Markdown with fixed sections | Jinja / dashboards | readable, durable, no hidden sections | no regenerate path; manual escaping |
| Render from runner `ctx` | build from run directory | data already in memory | can't rebuild; overclaimed docstring |
| `Agg` at import | object-oriented figures | headless rendering | process-wide backend side effect |
| Return `None` when nothing to plot | placeholder charts | never fabricate | none |
| Quantile bar chart | histogram / CDF | simple | weak view of the tail |
